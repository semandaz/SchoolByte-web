SchoolByte Quiz System: Comprehensive Design, Logic, and Feature Report
This document provides an exhaustive and granular breakdown of the SchoolByte quiz system, detailing its proposed database schemas, intricate backend logic, dynamic frontend interactions, and crucial operational considerations. The design principles are centered on delivering a fair, engaging, highly personalized, and challenging learning environment that ensures broad curriculum exposure, prevents content manipulation, fosters continuous content growth, and is built for future scalability.
I. Core Database Schemas: Detailed Breakdown & Enhancements
The foundation of the quiz system relies on a meticulously structured set of MongoDB/NoSQL collections, each serving a distinct purpose in storing and managing student, subject, quiz, and session data. We will also introduce enhancements for efficiency and expanded functionality.
1. Users Collection (for Students)
This collection holds all student-specific profiles and dynamic progress data. Its design is central to driving personalized quiz generation and tracking.
* _id: ObjectId
   * Purpose: The unique identifier for each student user document. This is automatically generated by MongoDB.
   * Constraint: Primary key, indexed.
* fullName: String
   * Purpose: The student's full name, for display on the dashboard and for administrative purposes.
* email: String
   * Purpose: The student's email address, used for login and communication.
   * Constraint: Must be unique across all users; indexed for efficient lookup.
* passwordHash: String
   * Purpose: Stores the securely hashed version of the student's password.
   * Constraint: Never store plaintext passwords. A strong hashing algorithm (e.g., bcrypt) must be used.
* role: String
   * Purpose: Defines the user's role within the platform.
   * Value: "student" (or "teacher" for faculty accounts).
* currentClass: String
   * Purpose: The student's current academic class level (e.g., "S.1", "S.2", ..., "S.6"). This field is foundational for determining the class-based distribution of quiz questions.
   * Constraint: Required field, captured during signup.
* subjectsEnrolled: Array of Strings
   * Purpose: A list of the specific subjects the student is officially enrolled in. This array is populated during signup based on class-level rules (compulsory + subsidiary/chosen). It drives the personalized display on the student dashboard.
   * Example: ["Mathematics", "English Language", "Biology"]
   * Constraint: Required. The number and type of subjects are validated at signup based on currentClass.
* bytesEarned: Number
   * Purpose: The cumulative total of "Bytes" (the in-platform currency/reward) earned by the student through successfully completed quiz questions.
   * Default Value: 0
* quizzesCompletedThisWeek: Number
   * Purpose: Counts the number of full 10-question quizzes completed by the student within the current calendar week. Used for implementing weekly quiz limits (if applicable, or for general tracking).
   * Default Value: 0 at the start of a new week.
* lastQuizResetDate: Date
   * Purpose: Stores the timestamp of the last time quizzesCompletedThisWeek was reset. This allows the system to determine when a new week has begun and if the counter needs to be cleared.
   * Example: Set to the Monday of the current week.
* recentQuizIds: Array of ObjectIds
   * Purpose: Implements the "sliding window" for preventing immediate question repetition. This array stores the _ids of the most recently completed quiz questions by this specific student.
   * Constraint: Has a fixed maximum size (e.g., 100-200 questions). When new _ids are added, the oldest ones are removed from the end of the array to maintain the size limit.
   * Enhancement: This array is crucial for the "fallback" mechanism where, once a student has exhausted the unique questions relevant to them, this list is reset (cleared), making all questions "new" to them again for repetition/reinforcement purposes.
* createdAt: Date
   * Purpose: Timestamp when the user account was created.
* updatedAt: Date
   * Purpose: Timestamp of the last update to the user document.
2. Subjects Collection
This static collection defines all the subjects available in the SchoolByte curriculum.
* _id: ObjectId
   * Purpose: Unique identifier for the subject document.
* name: String
   * Purpose: The full, human-readable name of the subject (e.g., "Mathematics", "Literature in English", "Agriculture"). This is the primary identifier used for linking across collections.
   * Constraint: Must be unique; indexed for efficient lookup.
   * Justification: Prioritizing human-readable names over serial numbers improves readability in the database, simplifies debugging, and aligns with how users naturally refer to subjects. Serial numbers, if needed, are secondary.
* serialNumber: Number (Optional)
   * Purpose: An arbitrary numerical identifier for the subject. Could be used for specific display ordering if alphabetical isn't desired, or for very niche internal optimizations.
   * Constraint: Unique.
* isCompulsory: Boolean
   * Purpose: Indicates if this subject is one of the 7 compulsory subjects for O'Level students.
   * Value: true or false.
* applicableLevels: Array of Strings
   * Purpose: Specifies which academic levels (O'Level Lower, O'Level Middle, A'Level) this subject's content is generally relevant to. Useful for filtering in admin panels or future features.
   * Example: ["O_Level_Lower", "O_Level_Middle", "A_Level"] for Mathematics.
3. Quizzes Collection (Quiz Questions)
This collection stores the definitions of all individual quiz questions available on the platform, including new fields for enhanced grading and content tagging.
* _id: ObjectId
   * Purpose: Unique identifier for each quiz question.
* questionText: String
   * Purpose: The primary text of the quiz question.
* questionType: String
   * Purpose: Defines the format of the question and dictates which specific answer fields are relevant.
   * Examples: "multiple-choice-single", "multiple-choice-multi", "short-answer", "true-false", "fill-in-the-blank", "matching", "ordering", "problem-solving", "numeric-entry".
* subject: String
   * Purpose: The subject this question belongs to.
   * Constraint: Must match a name from the Subjects collection. Indexed for querying.
* intendedClass: String
   * Purpose: The specific class level for which this question was designed and intended (e.g., "S.1", "S.3", "S.6"). This field is critical for the class-based question distribution logic.
   * Constraint: Must be one of the valid class strings. Indexed for efficient querying.
* maxBytesRewardPerQuestion: Number
   * Purpose: The maximum number of bytes a student can earn for correctly answering this specific question.
   * Enhancement: While each question contributes a maximum of 1 byte to the overall 10-byte quiz, this field allows for future flexibility if certain questions are deemed to have higher intrinsic value.
* Question Type Specific Fields (Examples):
   * options: Array of Objects (for multiple-choice-single, multiple-choice-multi)
      * [{ "text": "Option A", "isCorrect": true }, { "text": "Option B", "isCorrect": false }]
   * correctAnswers: Array of Strings (for short-answer, true-false, numeric-entry, fill-in-the-blank)
      * ["Paris"] or ["True"] or ["5"]
   * matchingPairs: Array of Objects (for matching)
      * [{ "itemA": "Author", "itemB": "Work" }]
   * orderedItems: Array of Strings (for ordering)
      * ["Event 1", "Event 2", "Event 3"]
* instructions: String (Optional)
   * Purpose: Specific instructions relevant to this particular question.
* hint: String (Optional)
   * Purpose: A hint provided for the question.
* explanation: String (Optional)
   * Purpose: A detailed explanation of the correct answer, provided to the student after their attempt. Crucial for learning and feedback.
* isActive: Boolean
   * Purpose: A flag to enable or disable the question for use in quizzes. Useful for content moderation or temporary removal.
   * Default Value: true.
* timesServedOverall: Number
   * Purpose: A global counter of how many times this specific quiz question has been presented to any student across the entire platform. Used for global content rotation and performance tracking.
   * Default Value: 0.
* lastServedTimestamp: Date
   * Purpose: The precise timestamp of the last time this question was served to any student. Used for global content rotation to prioritize older questions.
* Enhancement: Grading Keywords for Free-Form Answers
   * keywordsForGrading: Array of Strings (for short-answer, problem-solving)
      * Purpose: A list of essential keywords or short phrases that must be present in a student's free-form answer for it to be considered correct. These are used by the automated NLP-based grading system.
      * Example: ["sunlight", "chlorophyll", "water", "carbon dioxide", "glucose", "oxygen"]
   * negativeKeywords: Array of Strings (Optional, for short-answer, problem-solving)
      * Purpose: A list of terms or phrases that, if present in a student's answer, might indicate a misunderstanding or incorrect concept, leading to a deduction or invalidation of a match.
      * Example: For "Photosynthesis," ["night", "animals", "dark", "respiration"]
* Enhancement: Granular Content Tagging
   * topic: String (Optional)
      * Purpose: A broader thematic category within the subject (e.g., "Algebra", "Ecology", "World War II").
   * subTopic: String (Optional)
      * Purpose: A more specific categorization within a topic (e.g., "Quadratic Equations", "Food Chains", "Causes of WWII").
   * skillType: Array of Strings (Optional)
      * Purpose: Describes the cognitive skill required to answer the question (e.g., ["Memorization", "Application", "Analysis", "Problem-Solving"]).
* createdAt: Date
   * Purpose: Timestamp when the quiz question was created/uploaded.
* updatedAt: Date
   * Purpose: Timestamp of the last modification to the quiz question.
4. CompletedQuizAttempts Collection (Quiz Log)
This collection serves as an immutable log of every successfully completed quiz question by any student. This is crucial for analytics, audit trails, and preventing students from "fishing" for easy questions.
* _id: ObjectId
   * Purpose: Unique identifier for each completed attempt record.
* userId: ObjectId
   * Purpose: References the _id of the Users document, indicating which student made the attempt.
   * Constraint: Indexed for efficient querying by user.
* quizId: ObjectId
   * Purpose: References the _id of the Quizzes document, indicating which specific question was attempted.
   * Constraint: Indexed for efficient querying by question.
* studentClassAtAttempt: String
   * Purpose: A snapshot of the student's currentClass at the moment of this attempt. Useful for historical analysis of student progression.
* questionSubject: String
   * Purpose: A snapshot of the question's subject at the time of attempt.
* questionIntendedClass: String
   * Purpose: A snapshot of the question's intendedClass at the time of attempt.
* bytesAwarded: Number
   * Purpose: The actual bytes awarded for this specific attempt (can be fractional before final rounding).
* isSuccessful: Boolean
   * Purpose: true if the question was answered correctly (or above a defined partial success threshold), false otherwise.
* attemptDate: Date
   * Purpose: The exact timestamp when this question was submitted and processed.
* quizSessionId: ObjectId
   * Purpose: References the _id of the QuizSessions document it belonged to.
5. QuizSessions Collection (New Enhancement for currentQuizSession separation)
This new collection will encapsulate all real-time progress tracking for the "Fats and Beef" balancing mechanism, separated from the Users document for more efficient updates. Each document represents one 180-question cycle for a specific student.
* _id: ObjectId
   * Purpose: A unique identifier for the current 180-question balancing cycle. This ID is reset (a new one is generated) each time the session completes (after 180 questions) or is manually reset.
   * Constraint: Primary key.
* userId: ObjectId
   * Purpose: References the _id of the Users document.
   * Constraint: Indexed for efficient lookup.
* questionsCompletedCount: Number
   * Purpose: Tracks the total number of questions the student has completed within the _id session. This counter ranges from 0 up to 180.
   * Default Value: 0 at the start of a new session.
* subjectProgress: Object
   * Purpose: The heart of the "Fats and Beef" mechanism. It tracks, for each of the 18 global subjects, how many questions the student has completed from that subject within specific class-level categories during the current session.
Structure: Keys are subject names (e.g., "Mathematics", "Physics"). Values are objects:
"Mathematics": {
  "ownClass": 0,    // Questions whose `intendedClass` matches `user.currentClass`
  "lowerClass": 0,  // Questions whose `intendedClass` is lower (S1/S2 for S3 student)
  "higherClass": 0  // Questions whose `intendedClass` is higher (S4 for S3 student, or S5 for S4 student)
}
   *    * Counters: The ownClass, lowerClass, higherClass values are numbers, typically counting up to their respective quotas (e.g., ownClass to 5, lowerClass to 2, higherClass to 3 for each subject).
   * Default Value: All counters are 0 at the start of a new session.
* startedAt: Date
   * Purpose: Timestamp when this quiz session (180-question cycle) began.
* completedAt: Date (Optional)
   * Purpose: Timestamp when this quiz session (180-question cycle) was completed.
* updatedAt: Date
   * Purpose: Timestamp of the last update to this session document.
II. Class Level Definitions
For clarity and to drive the quiz generation logic, academic class levels are grouped:
* Lower O'Level: S.1, S.2
* Middle O'Level: S.3, S.4
* A'Level (Upper School): S.5, S.6
III. Quiz Generation Logic: A Deep Dive into the Backend Algorithm & Enhancements
When a student initiates a quiz, the backend orchestrates a sophisticated process to select 10 questions, prioritizing fairness, subject balance, content freshness, and intelligent repetition.
1. Initial Checks and Weekly Quiz Limits
Before question selection begins, the system performs critical pre-flight checks:
* Student Data Retrieval: The Users document for the requesting student is fetched. This provides currentClass, subjectsEnrolled, quizzesCompletedThisWeek, lastQuizResetDate, and the current quizSessionId to fetch the active QuizSessions document.
* Weekly Limit Enforcement:
   * Reset Check: The system compares user.lastQuizResetDate with the current date. If the current date falls into a new calendar week (e.g., today is Monday, and lastQuizResetDate was from the previous week's Monday or earlier), user.quizzesCompletedThisWeek is reset to 0, and user.lastQuizResetDate is updated to the start of the current week (e.g., current Monday 00:00:00 UTC). This update should occur atomically within the Users document.
   * Limit Check: The system then verifies user.quizzesCompletedThisWeek against a platform-defined maximum (e.g., 50 quizzes per week). If the student has already reached this limit, the quiz request is denied, and an appropriate message is returned to the frontend (e.g., "You have reached your weekly quiz limit. Please try again next week!").
   * Justification for Weekly Limits: This feature remains as an optional guardrail to prevent excessive "grinding" for bytes and to subtly encourage a balanced study approach. It's configurable, allowing platform administrators to adjust or disable it.
2. Determining Question Distribution Template (10 questions per quiz)
The system dynamically determines the proportion of questions from "own," "lower," and "higher/adjacent" classes based on the student's user.currentClass:
* O'Level Students (S.1, S.2, S.3, S.4): These students receive a blended quiz to expose them to content across the O'Level spectrum.
   * 5 questions: From the student's user.currentClass.
      * Example (S.3 student): 5 questions designed for S.3.
   * 2 questions: From a class "lower" than their user.currentClass.
      * Example (S.3 student): 2 questions from either S.1 or S.2, selected to be balanced over the 180-question cycle.
   * 3 questions: From a class "higher" than their user.currentClass.
      * Example (S.3 student): 3 questions from S.4.
      * Example (S.4 student): 3 questions from S.5 (as the next logical step into A'Level).
   * Justification: This distribution challenges students with slightly harder content while reinforcing foundational knowledge, crucial for comprehensive understanding at the O'Level.
* A'Level Students (S.5, S.6): These students receive questions focused on the A'Level curriculum.
   * 7 questions: From the student's user.currentClass.
      * Example (S.5 student): 7 questions designed for S.5.
   * 3 questions: From the adjacent A'Level class.
      * Example (S.5 student): 3 questions from S.6.
      * Example (S.6 student): 3 questions from S.5.
   * Justification: A-Level typically involves deeper specialization within a narrower band of subjects, so the distribution emphasizes their current class and the immediate adjacent advanced level.
3. Subject Balancing: The "Fats and Beef" Mechanism (The 180-Question Cycle)
This is the most sophisticated part of the algorithm, designed to ensure students cannot "game the system" by avoiding difficult or less preferred subjects and that every subject receives its due attention over time.
* The "Fats and Beef" Goal Explained: The system guarantees that, over a 180-question cycle (equivalent to 18 quizzes of 10 questions), the student will have completed a minimum number of questions from each of the 18 global subjects, specifically broken down by the class-level category (ownClass, lowerClass, higherClass).
* Calculation Breakdown:
   1. To ensure each of the 18 subjects gets 5 "own class" questions:
   2. To ensure each of the 18 subjects gets 2 "lower class" questions: 2textquestions/subjecttimes18textsubjects=36text"lowerclass"questions.
   3. To ensure each of the 18 subjects gets 3 "higher class" questions: 3textquestions/subjecttimes18textsubjects=54text"higherclass"questions.
   4. Total Cycle Length: 90(textown)+36(textlower)+54(texthigher)=textbf180questions. This is the Least Common Multiple (LCM) of the distribution components across all subjects, ensuring that theoretically, every "slot" for every subject/class-level is filled.
* Algorithm Steps for Question Selection:
   1. Identify Underrepresented Slots: The system first analyzes the active QuizSessions.subjectProgress document. For each of the 18 global subjects, it identifies if the counters for ownClass, lowerClass, or higherClass are below their respective minimum quotas (5, 2, or 3). These are the "underrepresented slots."
   2. Prioritization for 10 Quiz Slots: When filling the 10 questions for the current quiz, the system prioritizes selection as follows:
      * Highest Priority: "Underrepresented" Questions: It attempts to find questions that simultaneously fit one of the 10 quiz slots' class-level requirements (e.g., "needs a lower-class question") AND belong to a subject/class-level category that is currently "underrepresented" in QuizSessions.subjectProgress.
         * Crucial Justification: "Not Caring About Enrollment": It is a deliberate design decision that students will be assigned questions from subjects they are not formally subjectsEnrolled in, if that subject's subjectProgress counter for a specific class level is currently below its quota. This is the core of "Fats and Beef": it actively prevents students from avoiding certain topics or subjects (perhaps perceived as harder or less interesting) to maximize bytes. Every student must engage with the breadth of the curriculum over the 180-question cycle.
         * If multiple underrepresented subjects could fit a slot, a random selection among them can be made, or even prioritizing those most "behind."
      * Second Priority: subjectsEnrolled & Unseen Questions: If all "underrepresented" slots for the current quiz are filled, or no suitable questions are found for them, the system then focuses on selecting questions from the student's subjectsEnrolled list that are not in their user.recentQuizIds (unseen by this student) and fit the class distribution template.
      * Third Priority: Global Least-Served Questions (Intelligent Repetition Fallback): If finding new questions (from either underrepresented or enrolled subjects) becomes difficult, the system then broadens its search. It will select questions from Quizzes that have the lowest timesServedOverall or oldest lastServedTimestamp, even if they have been seen by this specific student (but not very recently, due to the sliding window).
         * Justification for Fallback/Repetition:
            * Finite Content Pool: Any curriculum has a finite set of unique questions, especially for specific class-subject combinations. Without intelligent repetition, the quiz stream would eventually dry up, halting learning progression.
            * Preventing Student Stalling: A student intensely focused on a narrow topic might exhaust unique questions quickly. Repetition ensures they can continue practicing.
            * Educational Reinforcement: Spaced repetition is a proven pedagogical technique. Re-encountering a concept/question after some time aids memory consolidation and highlights areas where mastery is not yet achieved. It transforms "repetition" from a bug into a powerful learning feature.
            * System Sustainability: Ensures a continuous supply of content and distributes question exposure across the entire user base over time.
         * Enhanced Fallback Trigger: If, after significant attempts, the system cannot find 10 suitable questions (either new or globally least-served from the Quizzes collection) that are not in the student's user.recentQuizIds, it will trigger a reset of the student's user.recentQuizIds array. This effectively makes all previously completed questions "new" again for that student, ensuring they always have content to engage with.
   3. Optimization for Querying: To enhance the efficiency of question selection, especially for the "underrepresented" and "global least-served" priorities, the backend should ensure:
      * Strategic Indexing: Comprehensive indexes on Quizzes.subject, Quizzes.intendedClass, Quizzes.isActive, Quizzes.timesServedOverall, and Quizzes.lastServedTimestamp are paramount.
      * Pre-computed Pools/Caching: For highly frequent query patterns (e.g., "all S.3 Math questions"), consider pre-computing and caching lists of quizIds or simplified question metadata.
* Final Quiz Assembly: Once 10 questions are selected, their _ids and necessary details (like questionText, questionType, options, etc., but not correct answers) are packaged and returned to the frontend.
4. Updates to Quizzes Collection During Generation (Asynchronous Enhancement)
For each question selected for a quiz:
* Its timesServedOverall field in the Quizzes collection is incremented.
* Its lastServedTimestamp is updated to the current time.
Enhancement: To prevent these updates from becoming a write hotspot on frequently served questions, these operations should ideally be performed asynchronously or in batches by a separate worker process. Instead of immediate, synchronous database writes, the quiz generation service could emit events (e.g., "question_served" events) to a message queue, and a dedicated "stats updater" service would consume these events and apply batched updates to the Quizzes collection. This decouples the real-time quiz serving from analytical counter updates, improving responsiveness and reducing contention.
IV. Quiz Submission & Progress Update Logic: Enhanced Reliability
This process is critical and only occurs upon successful completion and submission of a 10-question quiz. This prevents students from manipulating the system by cancelling quizzes. All updates spanning multiple documents will be handled within database transactions to ensure atomicity and data consistency.
1. Receive Submitted Answers
* The backend receives the student's answers for all 10 questions in the quiz. Each answer object will typically include questionId and studentAnswer.
2. Detailed Grading System (for all question types, including NLP for free-form)
The grading process is meticulously performed for each of the 10 submitted questions.
* A. Grading for Fixed-Answer Types (Multiple Choice, True/False, Numeric Entry, Matching, Ordering, Fill-in-the-Blank):
   * For each question, the submitted answer(s) are directly compared against the correctAnswers, options.isCorrect, matchingPairs, or orderedItems stored in the Quizzes collection.
   * bytesAwarded is either maxBytesRewardPerQuestion (if fully correct) or 0 (if incorrect), or a partial value for multi-select MCQs based on correctly selected options. isSuccessful is true or false.
* B. Grading for Free-Form Answer Types (Short Answer, Problem Solving):
   * This leverages advanced NLP for robust, partial credit scoring.
   * Student Answer Preprocessing: The student's submitted answer string undergoes an NLP pipeline:
      * Tokenization: Breaks the answer into individual words and phrases.
      * Normalization: Converts all text to lowercase, removes punctuation, and strips extra whitespace.
      * Stop Word Removal (Optional): Removes common, less meaningful words (e.g., "the", "a", "is"), unless they are part of a critical keyword phrase.
      * Lemmatization: Reduces words to their base or dictionary form (e.g., "running", "ran", "runs" all become "run"; "cells", "cellular" become "cell"). This enables matching variations of keywords.
   * Keyword Matching and Semantic Similarity: For each keyword from the teacher's keywordsForGrading list (fetched from the Quizzes document):
      * Exact Phrase Match: First, attempt to find the exact normalized keyword phrase within the student's processed answer.
      * Individual Word Match: If the keyword is a single word, check for its lemmatized form.
      * Teacher-Provided Synonyms Match: If the Quizzes schema is extended to allow teachers to provide explicit synonyms for keywords, check for these.
      * Semantic Similarity (Using Sentence Embeddings): This is the core intelligence.
         * Generate a vector embedding for each teacher keyword/phrase using a pre-trained Sentence Embedding model (e.g., Google's Universal Sentence Encoder, or a Sentence-BERT model).
         * Generate vector embeddings for meaningful segments (e.g., sentences, or noun phrases) within the student's processed answer.
         * Calculate the Cosine Similarity between the teacher keyword's embedding and all student answer segment embeddings.
         * If a student segment's embedding has a cosine similarity score above a high threshold (e.g., 0.85-0.90) with a teacher keyword's embedding, that keyword is considered "matched." This catches many synonyms and paraphrases.
   * Negative Keywords Check:
      * If the Quizzes document for this question contains negativeKeywords, the system will also check for their presence in the student's processed answer.
      * If a negative keyword is detected, it will either:
         * Deduct Points: Reduce the Individual Question Score by a small, predefined amount (e.g., -0.1 bytes) per negative keyword detected.
         * Invalidate Match: If a positive keyword is found but appears in a sentence segment that also contains a negative keyword, the match for that positive keyword might be invalidated, preventing credit for concepts used in incorrect contexts. This requires more sophisticated rule definition.
   * De-duplication: Ensure each keywordsForGrading concept is counted only once, even if mentioned multiple times or in various ways by the student.
   * Individual Question Byte Calculation: Individual Question Bytes = (Count of uniquely matched positive keywords / Total count of teacher's positive keywords) * 1 (since each question carries 1 byte). Deductions for negative keywords are applied here.
* C. Overall Quiz Byte Calculation & Rounding:
   * The bytesAwarded for all 10 questions are summed up.
   * Total Quiz Bytes = Σ (Individual Question Bytes for all 10 questions)
   * Rounding: The Total Quiz Bytes will then be rounded to the nearest whole number (e.g., using Math.round() in JavaScript or similar in backend) before being added to user.bytesEarned. This ensures byte currency is easily managed and displayed.
3. Log CompletedQuizAttempts
* For each of the 10 questions in the submitted quiz, a new document is created in the CompletedQuizAttempts collection. This record serves as an immutable log and includes: userId, quizId, studentClassAtAttempt, questionSubject, questionIntendedClass, bytesAwarded (the fractional/calculated value for that specific question), isSuccessful (for that question), attemptDate, and the quizSessionId from the student's Users document. This multi-document insertion should be part of the transaction.
4. Update Student's Users and QuizSessions Documents
* Users Document Update (within transaction):
   * bytesEarned: The final rounded Total Quiz Bytes (from step 2C) is added to user.bytesEarned.
   * quizzesCompletedThisWeek: This counter is incremented by 1.
   * recentQuizIds (Sliding Window Update): The _ids of the 10 completed quiz questions are added to the beginning of the user.recentQuizIds array. If the array's size now exceeds the predefined limit (e.g., 100 or 200), the necessary number of _ids are removed from the end of the array to maintain the limit, using efficient array operators ($push with $slice in MongoDB).
* QuizSessions Document Update (within transaction):
   * The active QuizSessions document (identified by quizSessionId from the Users document) is fetched and updated.
   * questionsCompletedCount: This counter is incremented by 10.
   * subjectProgress: For each of the 10 questions, the corresponding ownClass, lowerClass, or higherClass counter within the specific subject object in subjectProgress is incremented.
* QuizSessions Reset Trigger (within transaction): After updating questionsCompletedCount, the system checks if it has reached or exceeded 180. If so:
   * The current QuizSessions document is marked as completed (e.g., by setting completedAt timestamp).
   * A new QuizSessions document is created with questionsCompletedCount reset to 0, subjectProgress entirely reset (all subject and class-level counters within it are set back to 0), and a new ObjectId() generated for its _id.
   * The user.currentQuizSessionId in the Users document is updated to point to this new QuizSessions document.
   * Justification for 180-Question Reset: This ensures a complete "fats and beef" cycle, where the student is guaranteed to have encountered content from every subject across the various class-level difficulties at least the minimum number of times. It provides a clean slate for the next balancing cycle.
V. Teacher Responsibilities: Content Contribution & Quality Assurance
To ensure a vibrant and ever-growing pool of content, teachers will have a responsibility to contribute new quiz questions regularly, backed by automated and human-centric quality checks.
1. Minimum Weekly Quiz Contributions
* Platform Goal: The SchoolByte platform will establish a target for the minimum number of new quiz questions a teacher must add weekly (e.g., 5-10 new questions per teacher per week).
* Tracking Mechanism (Backend): A Teachers collection (or dedicated fields within the Users document for role: "teacher") could store fields like quizzesUploadedThisWeek and lastUploadResetDate. Alternatively, a TeacherActivityLog collection could record each quiz upload event, allowing aggregate weekly counts.
* Reporting (Frontend): This metric (quizzesUploadedThisWeek) can be displayed prominently on the teacher's dashboard, showing their current contribution towards the weekly goal. This fosters accountability and encourages consistent content creation.
2. Automated Duplicate Detection (Crucial for Content Quality)
This is a two-tiered system to prevent redundant questions from entering the content pool, streamlining the content management process.
* A. First Pass: Exact Duplicate Detection (Hashing)
   * Mechanism: When a teacher uploads a new question, the backend will generate a unique cryptographic hash (e.g., SHA-256) of the questionText (after normalization, such as trimming whitespace and lowercasing).
   * Detection: Before saving the new question, the system will perform a rapid lookup to see if an identical SHA-256 hash already exists in a dedicated QuestionHashes collection or within the Quizzes document itself (indexed for speed).
   * Outcome: If an exact hash match is found, the upload is immediately flagged as a direct duplicate. The teacher is notified on the frontend with a message like: "This question appears to be an exact duplicate of an existing question. Please review and modify if you still wish to submit." (An override option with clear warning can be provided for rare legitimate cases).
* B. Second Pass: Semantic Similarity Detection (NLP - Sentence Embeddings)
   * Mechanism: If no exact hash match is found, the system proceeds to a deeper semantic analysis.
      * The new questionText is fed into a pre-trained Sentence Embedding model (e.g., Universal Sentence Encoder by Google, or a Sentence-BERT model). This model transforms the entire question into a high-dimensional numerical vector that encapsulates its meaning.
      * This new question's embedding is then compared (using Cosine Similarity) against embeddings of existing questions within the same subject and intendedClass (to narrow the comparison scope for efficiency).
   * Detection: If the cosine similarity score between the new question's embedding and an existing question's embedding exceeds a predefined high threshold (e.g., 0.85-0.90), it is flagged as a potential semantic duplicate.
   * Outcome: These potential_semantic_duplicate questions are not immediately made isActive. Instead, they are routed to a Manual Review Queue.
3. Manual Review Queue
* Purpose: Provides human oversight for questions flagged as potential duplicates by the semantic similarity check, or for any content moderation needs.
* Access: A dedicated administrator or lead teacher dashboard will display this queue.
* Workflow:
   * Reviewers see the newly submitted question side-by-side with the existing question(s) it was flagged against.
   * Reviewers can take actions:
      * Approve: If it's not a true duplicate, or if the new wording/content offers a significant improvement/fresh perspective, mark it isActive.
      * Reject: If it's a clear semantic duplicate, permanently reject the new submission.
      * Merge/Archive: In advanced scenarios, a feature to merge the new content into an existing question (e.g., incorporating better options or hints) or to archive the new version might be considered.
* Justification: Human judgment is indispensable for nuanced language understanding and ensures the highest quality of content. Automated flagging helps keep the manual review queue manageable.
