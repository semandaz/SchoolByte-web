SchoolByte Platform: Detailed Vision Report (Updated with Full Illustrations)
This report consolidates all the information you have provided regarding your vision for the SchoolByte educational platform, detailing its purpose, user roles, specific features, and how various interactions should function.

1. Core Vision and Purpose
SchoolByte is envisioned as an innovative and engaging educational platform designed to:

Motivate Student Learning: Through a unique "bytes" reward system, students are incentivized to engage with educational content and achieve academic and personal growth.

Empower Teachers: Provide teachers with robust tools to create, manage, and deliver diverse learning materials and assessments efficiently.

Streamline Administration: Offer administrators comprehensive control over user accounts, content, and platform maintenance, ensuring smooth operation.

Foster Continuous Improvement: Implement mechanisms for feedback, revision, and progressive learning, adapting to student needs and performance.

2. User Roles and Their Envisioned Functionalities
SchoolByte is designed for three distinct user types: Students, Teachers, and Administrators, each with tailored functionalities.

2.1. Students
Students are the primary users, interacting with content and earning rewards.

Account Management & Profile:

Registration: Students sign up with their studentName, unique indexNumber, email, and password. They also provide their class, stream, and classTeacher for organizational purposes within the school structure.

Email Verification: A mandatory step for login. After registration, a unique 6-digit code is sent to their provided email address. Students must enter this code within 10 minutes to verify their email and enable login.

Login: Secure access to their personalized dashboard after successful email verification.

Dashboard: A central hub to view their current bytes balance (new students start with 20 bytes), academic details, and other personal information.

Preferences: Ability to customize their user experience, including fontSize (e.g., "small", "medium", "large"), theme (e.g., "light", "dark"), and notifications_on (boolean) settings.

Leaderboard Display Name: Students can set a firstNameDisplay for the leaderboard. If not set, their actual first name (derived from studentName) will be used by default on the leaderboard.

Learning & Engagement:

WorkFiles: Students can access and download PDF WorkFiles uploaded by teachers. These serve as reference materials for activities or general study.

Activities (Long-Answer Tasks):

Engagement: Students interact with long-answer questions dynamically rendered on the frontend based on teacher-defined activity data. They are prompted to provide detailed textual answers.

Submission: Students type their comprehensive answers into provided input fields for each question.

Automated Grading: The backend automatically grades submissions by comparing the student's answer text against keywordsForMarking (an array of strings) provided by the teacher for each question. The system checks if the student's answer contains these keywords.

Byte Awarding:

Initial Attempt: Students earn the full maxBytesReward (fixed at 5 bytes) for successfully passing an activity on their very first attempt (passing threshold is 70% overall score based on keyword matching).

Revision/Re-earning: If a student fails their initial attempt (score below 70%), they become eligible to re-earn the full 5 bytes if they pass a subsequent revision attempt after 14 days from their initial attempt. If they pass a revision attempt within 14 days of their initial failure, or if their initial attempt was a pass, no additional bytes are awarded for that activity, but they can still practice.

Keyword Revelation: If a student fails a revision attempt (regardless of whether it's within or after the 14-day window), the system will reveal the keywordsForMarking for the questions they answered incorrectly. This mechanism is designed to aid their revision and guide them towards the correct concepts.

Quizzes:

Random Quiz Generation: When a student visits the quizzes section, the system will randomly select 10 QuizQuestions from the database that match the student's class and/or subject filters (if applied). This set of 10 questions refreshes every time the quizzes section is visited, even if the student doesn't submit answers for scoring.

Frontend-Driven Display (Your Vivid Illustration):

The teacher, during question creation, selects an "answer type" (e.g., "fill-in-the-blank," "multiple-choice-single," "multiple-choice-multi", "true-false", "matching", "ordering", "problem-solving") on the frontend. This selection is sent to the database and stored as the type field (e.g., 'fill-in-the-blank', 'multiple-choice-single').

Example: Fill-in-the-Blank: The teacher types "I am ____ boy" as the questionText and "a" as the correctAnswer. When the student's frontend receives this QuizQuestion from the database, it uses the type field ('fill-in-the-blank') to dynamically render "I am ____ boy" with a blank space for the student to type. Crucially, the student's frontend only sends back the actual string typed in the blank space (e.g., "a"), NOT the "fill-in-the-blank" answer type. The backend then marks this submitted string against the teacher's correctAnswer.

Example: Multiple-Choice (Single/Multi): The teacher types in the different options (e.g., "Option A", "Option B") and marks which one(s) are isCorrect. The student's frontend displays these as clickable options (e.g., radio buttons or checkboxes). The student's frontend then only sends back the string/ID of the chosen option(s), NOT the "multiple-choice" answer type. The backend marks this choice against the stored correct option IDs.

Example: Matching: Teacher provides pairs (e.g., {itemA: "Capital of Uganda", itemB: "Kampala"}). Frontend displays two columns, student drags/selects to match. Frontend sends back student's pairs.

Example: Ordering: Teacher provides items in correct order (e.g., ["First", "Second", "Third"]). Frontend displays scrambled items, student reorders. Frontend sends back student's ordered list.

Scoring & Bytes (Quizzes): Each correctly answered quiz question is worth 1 byte. A full quiz session of 10 questions can yield a maximum of 10 bytes. The overall bytes earned for a quiz session are calculated as "total correct questions divided by total attempted questions, multiplied by 10 bytes" (e.g., 7 correct out of 10 = (7/10) * 10 bytes = 7 bytes).

Preader Games (Interactive Stories):

Concept: Fully AI-driven interactive narrative games where students make choices that influence the story's progression, their character's development, and the ultimate outcome. The stories are designed to be novel-like, immersive, and set within a Ugandan secondary school context.

AI Generation: The entire narrative, including vivid scene descriptions, realistic dialogue, and complex plot twists, is generated dynamically by Google Gemini 1.5 Flash. The AI is specifically prompted to:

Use common Ugandan names (e.g., Aisha, Okello, Nalwoga, Mugisha).

Describe typical Ugandan school environments (e.g., dusty assembly grounds, corrugated iron roofs, prep time, school canteen).

Incorporate local terminology naturally (e.g., "mwalimu," "boda-boda," "chapati").

Introduce "hard twists" – unexpected, impactful, and often morally complex events that challenge the player and drive the narrative.

Dynamic Player Stats: Students track 8 core stats that influence choices and narrative branches:

Life (Physical & Mental Well-being, if it hits 0, game over)

Mana (Cognitive Energy/Focus)

Morale (Social Confidence & Emotional Resilience)

Reputation (Social Standing, can be positive or negative)

Discipline (Self-Control & Adherence to Rules, capped 0-100)

Knowledge (Academic Progress)

Stress (Emotional Burden, can increase)

Luck (Chance/Fortune, influences probabilistic choices)

Choices made by the student directly impact these stats.

Choice & Consequence with Interconnected Events (Your Illustration):

The game is designed so that seemingly minor "by the way" choices can have significant, long-term consequences.

Example: The "Stepping on Shoes" Incident:

A student (e.g., "Aisha") is walking down the corridor, and another student accidentally steps on her shoes.

Choice A: Slap the guy. This choice immediately impacts Aisha's stats (e.g., Discipline -15, Reputation -10, Stress +15, Life -5 due to the ensuing confrontation). The consequence is that the "guy reports you to the school administration." Aisha is "held there for a long period."

Impact on Compulsory Event (The Exam): Because of the detention, Aisha "loses 30 minutes of the paper" when she finally enters the exam room. This directly affects her options: "What do you do? Cheat, DIY, or other funny options." The AI generates these choices, and their outcomes are influenced by Aisha's current stressed state, low discipline, and lost time.

Choice B: Walk away / Politely resolve. This choice might have minor positive or negative stat impacts (e.g., Morale +5, Stress -2, Discipline +5). Aisha proceeds to the exam calmly, with full time and a clear mind, leading to different, potentially more favorable choices and outcomes during the exam (e.g., "Methodically work through each question," "Tackle hardest questions first").

Ethical Scoring: A currentEthicalScore is maintained throughout the game, accumulating positive or negative points based on the moral implications of the student's choices. This score is a key factor in the final byte reward. Even if a student reaches a "Game Over" state, their ethicalScore is still assessed and contribute to any minimal bytes earned, teaching nuanced morality.

Rewind Feature: Students can "rewind" their last decision, reverting to the state before that choice was made (including stats and ethical score). This costs 5 bytes per rewind, allowing for experimentation and learning from mistakes without severe permanent consequences.

Predetermined Ending Point, Variable Journeys & Outcomes (Your Clarification):

All choices do NOT lead to the exact same ending. Instead, all players will eventually reach a common final plot point or narrative conclusion (e.g., "The End of the School Year Ceremony," "Graduation Day"). This provides a structural anchor for the story.

However, the journey to that ending, the specific narrative details within that final scene, and the bytes earned are highly variable.

Example: "Student of the Year" Goal: The "Student of the Year" is the ultimate goal, achieved by successfully balancing high Knowledge, Reputation, Discipline, and a positive currentEthicalScore throughout the game. This path yields the maximum byte reward.

Other Endings: Depending on the choices made and the resulting stat values, a student might reach the "End of the School Year" as:

The "Student of the Year" (optimal path, maximum bytes).

A "Good Effort" student (completed, but didn't excel in all areas, moderate bytes).

A "Struggling but Surviving" student (faced many challenges, lower bytes).

Or, if Life dropped to zero earlier, they might have reached a "Failure Ending" (e.g., "The Burnout Ending," "The Expulsion Ending" due to disciplinary issues like the slap incident). These failure endings narrate the consequences of poor choices or unmanaged stress and yield minimal bytes.

The Difference: The student who didn't slap the guy might maintain high Discipline and low Stress, allowing them to perform well in the exam, gain Knowledge, build Reputation, and ultimately flow towards the "Student of the Year" path, earning significantly more bytes. The "slapper" might miss exam time, forcing tough "cheat, DIY, or funny options," leading to lower Knowledge, higher Stress, and a less successful outcome, potentially even a "Failure Ending" like expulsion. This ensures that choices truly matter and lead to distinct experiences and rewards, even if the narrative concludes at a similar conceptual point.

Leaderboards: Students can view their ranking on a global leaderboard, with their firstNameDisplay (or first name) and bytes visible. Only the top 200 students' byte counts are displayed; others are shown without a specific byte count (e.g., "Undefined" or similar), to encourage competition among the top tier while still including all students.

2.2. Teachers
Teachers are responsible for content creation and management.

Account Management:

Login: Secure access to their dashboard.

Initial Password Setup: For teachers whose accounts are created by administrators, they must set their own secure password on their very first login. Their account is initially marked with isPasswordSet: false.

Dashboard: Access to their profile, content management tools, and their own bytes balance (teachers start with 0 bytes).

Preferences: Customize their interface settings, similar to students.

Content Creation & Management:

WorkFile & Activity Upload:

Teachers upload PDF WorkFiles (e.g., notes, assignments, worksheets).

Simultaneously, they define an Activity linked to that WorkFile, including its title, description, subject, intendedClass (e.g., "S.1"), costBytes (for students to download the PDF), and a critical array of questions.

Each question within an Activity includes questionText and an array of keywordsForMarking (e.g., ["photosynthesis", "chlorophyll", "light energy"]) for automated grading.

Teachers can specify whether the downloaded WorkFile PDF should have a watermark (applyDownloadWatermark: true/false).

This entire upload process is atomic: if any part (PDF upload to Cloudinary, WorkFile save to MongoDB, Activity save to MongoDB, or linking the Activity ID back to the WorkFile) fails, the entire transaction is rolled back to prevent inconsistent data.

Quiz Question Management (CRUD): Teachers have full control over individual quiz questions:

Create: Add new quiz questions, specifying questionText, subject, intendedClass, type (e.g., 'short-answer', 'multiple-choice-single', 'fill-in-the-blank', 'matching', 'ordering', 'true-false', 'problem-solving'). Based on the type, they provide the corresponding data:

options: For multiple-choice, an array of { text: string, isCorrect: boolean }.

correctAnswers: For short-answer, true-false, fill-in-the-blank, problem-solving, an array of correct string answers.

matchingPairs: For matching, an array of { itemA: string, itemB: string }.

orderedItems: For ordering, an array of strings in the correct sequence.

Each question has a maxBytesRewardPerQuestion (defaulting to 1 byte).

Read: View all their uploaded quiz questions, with filtering options by subject or intendedClass. They can also fetch a single question by ID for detailed viewing and editing.

Update: Modify existing quiz questions, including their type and associated answer structures (e.g., changing options for a multiple-choice question).

Delete: Remove quiz questions.

Leaderboards: Teachers can view a leaderboard of teacher byte rankings.

2.3. Administrators
Administrators oversee the platform, manage users, and perform system-level tasks.

Account Management:

Login with 2FA: Administrators log in with their email and password. Upon successful password verification, a 6-digit Two-Factor Authentication (2FA) code is immediately sent to their registered email. They must then enter this code into a separate verification step to gain full access and receive their JWT. The 2FA code expires after 10 minutes.

Teacher Management:

Create Teachers: Administrators can create new teacher accounts, providing teacherName, email, initialPassword, gender, and an optional physicalDescription. New teacher accounts are initially marked with isPasswordSet: false, requiring the teacher to set their own secure password on their very first login.

View Teachers: Access a list of all registered teachers, including their details (excluding passwords).

Delete Teachers: Administrators can delete teacher accounts. When a teacher is deleted, all content (WorkFiles, Activities, QuizQuestions, PreaderGames) they uploaded remains on the platform, but the teacherId link is nullified (set to null), while the teacherName remains for attribution purposes.

Student Data Management:

Yearly Class Upgrade/Deletion: A dedicated endpoint (intended to be triggered annually, e.g., via a cron job, but manually triggerable by admin) automatically:

Deletes the accounts of all students in S.6 (Senior 6), simulating graduation.

Upgrades students from S.1 to S.5 to their next respective class level (e.g., S.1 to S.2, S.5 to S.6).

Preader Game Management:

Create Preader Games: Administrators can create new Preader Game templates by providing a title, description, genre, maxBytesReward, and crucially, an initialAiPrompt and ugandanSchoolContext. Upon creation, the backend will use the AI to generate the first StoryNode (scene and choices) based on these prompts, linking it to the new game.

View Preader Games: Access a list of all Preader Game templates, including those in draft status.

Update Preader Game Status: Change the status of a Preader Game (e.g., from draft to published to make it available to students, or archived).

Delete Preader Games: Delete a Preader Game template and all its associated StoryNodes and PreaderGameSessions from the database.

3. Technical Architecture (Backend)
The SchoolByte backend is built on a robust Node.js and Express.js framework, utilizing MongoDB with Mongoose for data persistence.

Core Technologies: Node.js, Express.js, MongoDB (Mongoose ODM), JWT (for authentication), bcrypt (for password hashing).

Email Service: Nodemailer for sending transactional emails (email verification codes, admin 2FA codes).

File Storage: Cloudinary for secure and scalable storage of WorkFile PDFs. Integrated via Multer for handling multipart form data during file uploads.

AI Integration: Google Generative AI SDK (Gemini 1.5 Flash) is directly integrated for dynamic content generation in Preader Games, enabling complex narratives and choices, and ensuring Ugandan school context is consistently applied through prompt engineering.

Data Integrity: Extensive use of express-validator for API input validation to ensure data quality. MongoDB transactions are employed for atomic operations (e.g., WorkFile/Activity upload, Preader Game progression), ensuring data consistency across multiple related database documents.

Security: Helmet middleware is used for setting various HTTP security headers, enhancing the application's overall security posture.

Logging: Morgan middleware provides HTTP request logging for development and debugging purposes.
